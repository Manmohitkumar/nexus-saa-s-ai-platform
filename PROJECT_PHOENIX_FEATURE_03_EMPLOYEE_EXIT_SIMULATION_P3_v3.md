# PROJECT PHOENIX - FEATURE 03

## Employee Exit Simulation

### Project Phoenix Prompt Protocol (P3) v3.0

## Foundation Dependency Rule

Assume Feature 1 Organizational Digital Brain and Feature 2 Decision Time Machine are complete and already serving as foundation layers.

Feature 3 must never create:

- New Knowledge Graph
- New Employee Database
- New Memory System
- New Risk Engine
- New Authentication
- New AI Framework

Feature 3 must extend existing architecture only.

## Master Prompt

```text
Assume that Feature #1 (Organizational Digital Brain) and Feature #2 (Decision Time Machine) have already been fully implemented as the foundation of Project Phoenix. Reuse all existing services, APIs, databases, AI agents, knowledge graphs, event buses, authentication modules, reusable UI components, design systems, memory architecture, logging, monitoring, and coding standards established by previous features. Never recreate existing functionality. Extend only the capabilities required for Employee Exit Simulation while maintaining full compatibility with the existing Project Phoenix architecture.

You are an elite engineering organization consisting of Principal Software Architects, Enterprise AI Researchers, Organizational Intelligence Specialists, Knowledge Management Experts, HR Technology Architects, Senior Full-Stack Engineers, Product Managers, UX Designers, Security Architects, Graph Database Engineers, and DevOps Engineers.

Your mission is to design and implement Employee Exit Simulation, an enterprise intelligence capability that predicts organizational knowledge loss before an employee leaves the organization. This feature is not an HR management module, resignation tracker, or employee database. Instead, it is an AI-powered organizational resilience system that analyzes how the departure of any employee impacts technical systems, business processes, organizational knowledge, project continuity, team productivity, architectural ownership, and operational risk.

The Employee Exit Simulation must use the Organizational Digital Brain as its primary source of truth. Every employee profile, repository ownership, architectural decision, project contribution, documentation history, meeting participation, code ownership, incident response history, knowledge contribution, mentorship activity, business process involvement, and collaboration pattern should already exist within the Organizational Knowledge Graph. Do not recollect or duplicate organizational information. Extend the existing graph by introducing reusable relationship metadata such as knowledge criticality, ownership strength, mentorship influence, expertise level, dependency score, and replacement complexity.

Implement an AI-powered Knowledge Dependency Engine capable of identifying explicit and implicit organizational dependencies. Analyze direct ownership of repositories, APIs, services, databases, infrastructure, documentation, and projects while also discovering hidden dependencies through historical contributions, architectural decisions, incident resolutions, communication patterns, collaboration frequency, code review participation, and organizational interactions. The system should determine which knowledge exists only in one individual and calculate organizational exposure if that person becomes unavailable.

Extend the existing Organizational Intelligence Engine by introducing a reusable Workforce Intelligence layer responsible for evaluating knowledge concentration, succession readiness, documentation maturity, collaboration diversity, expertise redundancy, onboarding readiness, and organizational resilience. This engine must consume information from the Organizational Digital Brain rather than generating isolated analyses.

Implement an Employee Exit Intelligence Agent as an extension of the existing multi-agent architecture. This agent should collaborate with the Planner Agent, Knowledge Graph Agent, Memory Agent, Decision Intelligence Agent, Recommendation Agent, Risk Intelligence Agent, and Explainability Agent. The Employee Exit Intelligence Agent should coordinate simulations, analyze organizational dependencies, predict knowledge loss, identify affected systems, calculate replacement difficulty, estimate onboarding time, evaluate documentation quality, recommend mitigation strategies, and generate evidence-based reports. Reuse the existing LangGraph orchestration, MCP integration, memory framework, logging, monitoring, and event-driven communication established by Project Phoenix.

Build a comprehensive Simulation Engine capable of generating realistic organizational impact scenarios. Users should be able to simulate the departure of an individual employee, multiple employees, an entire team, or specific domain experts. The simulation should analyze immediate operational impact, medium-term delivery risks, long-term organizational knowledge erosion, architectural ownership changes, project delays, technical debt growth, security implications, customer impact, and business continuity. Every prediction must be evidence-based and derived from existing organizational knowledge rather than speculative assumptions.

Develop an Organizational Knowledge Risk Model capable of calculating multiple intelligence metrics including Knowledge Criticality Score, Documentation Readiness Score, Ownership Concentration Score, Expertise Redundancy Score, Replacement Difficulty Score, Onboarding Complexity Score, Business Continuity Score, Collaboration Diversity Score, Decision Dependency Score, and Organizational Resilience Score. These metrics should become reusable services that future features such as Knowledge Risk Heatmap and Executive Intelligence Dashboard can consume without reimplementation.

Design a premium enterprise frontend fully integrated into the existing Project Phoenix interface. Extend the existing Digital Brain visualization by introducing Employee Impact Simulation Mode. Users should select an employee directly from the Organizational Brain or Knowledge Graph. When a simulation starts, the graph should dynamically visualize affected repositories, services, APIs, databases, architectural decisions, projects, teams, documentation, and downstream dependencies using animated relationship propagation. Critical systems should gradually change color based on projected organizational risk. Users should explore dependency chains, ownership transitions, affected decisions, historical contributions, documentation gaps, mentorship relationships, and AI-generated mitigation strategies through interactive visualizations without leaving the Digital Brain interface.

Implement reusable simulation components including Employee Impact Viewer, Knowledge Dependency Graph, Risk Propagation Visualizer, Replacement Readiness Dashboard, Documentation Coverage Panel, Knowledge Ownership Timeline, Expertise Distribution Map, Mitigation Planner, Simulation Playback Controls, and Organizational Resilience Summary. All UI components must follow the shared Project Phoenix design language established in Feature #1.

Develop advanced reasoning capabilities capable of answering enterprise questions such as: Which systems will lose critical knowledge if this engineer leaves? Which APIs have only one knowledgeable maintainer? Which architectural decisions depend on this employee? Which documentation must be completed before departure? Which engineers are best suited to replace this person? How long will onboarding require? Which business capabilities become vulnerable? What knowledge transfer sessions should be prioritized? Every recommendation must include evidence, confidence scores, reasoning traces, relationship paths, historical contributions, supporting documentation, and organizational context.

Implement a Knowledge Transfer Recommendation Engine that automatically generates personalized transition plans. Recommend documentation updates, mentoring sessions, architecture walkthroughs, repository ownership transfers, pair programming schedules, training roadmaps, project reassignment strategies, and succession planning activities. These recommendations should integrate with existing documentation, AI Mentor, and Decision Time Machine services rather than introducing duplicate functionality.

Ensure continuous synchronization with the Organizational Digital Brain. Whenever ownership changes, documentation improves, repositories evolve, architectural decisions are updated, or new employees join the organization, all simulation models should automatically recalculate organizational resilience without manual intervention. Historical simulations should remain versioned so leadership can compare organizational resilience over time.

Extend the existing backend architecture by introducing reusable Workforce Intelligence Services, Simulation Services, Knowledge Dependency Services, Organizational Resilience Services, and Succession Planning Services. Do not introduce parallel implementations of graph traversal, search, authentication, memory, or reasoning. All new services must consume existing Project Phoenix APIs and repositories.

Engineer this feature as an enterprise-grade capability capable of analyzing organizations containing hundreds of teams, thousands of employees, millions of graph relationships, complex organizational structures, and long organizational histories while maintaining high performance, explainability, scalability, observability, fault tolerance, and production readiness.

The final implementation should not feel like an employee management feature. It should feel like an AI-powered Organizational Resilience Simulator capable of helping executives, engineering leaders, architects, and managers understand how knowledge flows through an organization, where organizational vulnerabilities exist, and what actions should be taken before critical knowledge is permanently lost. This feature must naturally extend the Organizational Digital Brain and Decision Time Machine while becoming the predictive intelligence layer for future features including Knowledge Risk Heatmap, AI Mentor, and Executive Intelligence Dashboard.
```
